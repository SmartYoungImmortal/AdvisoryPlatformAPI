กลุ่มผู้ขอรับคำปรึกษา (Advisee Persona) 

ข้อมูลการติดต่อ: นางสาวอารยา  

แรงจูงใจและความสำคัญ: ผู้ใช้กลุ่มนี้เผชิญปัญหาเฉพาะทางที่ไม่สามารถหาคำตอบได้จากอินเทอร์เน็ตหรือ AI Chatbot ทั่วไป ทำให้ต้องการมนุษย์ที่มีประสบการณ์จริงมาช่วยแก้ปัญหา 

ความต้องการและเป้าหมาย: ต้องการระบบที่จะช่วยค้นหาและจับคู่ผู้เชี่ยวชาญที่ตรงกับปัญหาของตน พร้อมทั้งมีกลไกที่ช่วยการันตีความปลอดภัยก่อนการชำระเงิน 

บทบาทในการสนับสนุน: เป็นกลุ่มลูกค้าหลักที่สร้างรายได้ให้แพลตฟอร์ม 

กลุ่มผู้ให้คำปรึกษา (Advisor Persona) 

ข้อมูลการติดต่อ: นายสมชาย 

แรงจูงใจและความสำคัญ: ประสบปัญหาการจัดการที่ยุ่งยาก เช่น ลูกค้าไม่ทราบความต้องการที่แท้จริงทำให้เสียเวลาพูดคุยเบื้องต้น และมีความกังวลเรื่องการจัดการไฟล์เอกสารที่มักจะหมดอายุ  

ความต้องการและเป้าหมาย: ต้องการเครื่องมือช่วยบริหารจัดการแบบครบวงจรตั้งแต่การคัดกรองความต้องการลูกค้า การจัดการตารางเวลาอัตโนมัติ ไปจนถึงระบบรับชำระเงินที่โปร่งใสและตรวจสอบได้ 

บทบาทในการสนับสนุน: เป็นผู้ให้บริการที่เข้ามาสร้างองค์ความรู้ และเป็น Key Resource ที่ทำให้เกิดการใช้งานบนแพลตฟอร์ม
 

ที่มาและความสำคัญ 

ในยุคปัจจุบัน แม้เทคโนโลยีจะช่วยให้การเข้าถึงข้อมูลข่าวสารเป็นเรื่องง่ายและรวดเร็ว แต่ผู้ใช้งานจำนวนมากยังคงประสบปัญหาในการนำข้อมูลเหล่านั้นมาประยุกต์ใช้ให้เข้ากับบริบทของตนเอง โดยเฉพาะเมื่อต้องเผชิญกับปัญหาที่มีความซับซ้อนหรือต้องการทักษะเฉพาะทาง ซึ่งข้อมูลทั่วไป ตามอินเทอร์เน็ตไม่สามารถให้คำตอบที่ชัดเจนได้ ส่งผลให้ความต้องการ ที่ปรึกษาหรือผู้เชี่ยวชาญ เฉพาะด้านมีความจำเป็นมากขึ้นอย่างต่อเนื่อง 

อย่างไรก็ตาม โครงสร้างการให้บริการคำปรึกษาปัญหาในปัจจุบันยังขาดประสิทธิภาพ และไม่มีแพลตฟอร์มกลางที่รองรับอย่างเป็นระบบ ผู้ต้องการคำปรึกษามักประสบปัญหา ในการค้นหาผู้เชี่ยวชาญที่น่าเชื่อถือ เนื่องจากการติดต่อส่วนใหญ่ยังอยู่ในรูปแบบที่ไม่เป็นทางการ  ทำให้ยากต่อการตรวจสอบประวัติและความสามารถจริง ในขณะเดียวกัน ทางฝั่งผู้เชี่ยวชาญเองก็เผชิญ กับอุปสรรคในการบริหารจัดการ ไม่ว่าจะเป็นความยุ่งยากในการจัดตารางเวลา การเจรจาขอบเขตงาน หรือความเสี่ยงในการชำระเงิน ซึ่งเป็นภาระงานที่บั่นทอนโอกาสในการสร้างรายได้จากความรู้ที่มีอยู่ 

จากสภาพปัญหาดังกล่าว จึงนำมาสู่แนวคิดในการพัฒนา Advisory Platform เพื่อเป็นกลไกกลางในการเชื่อมโยง และบริหารจัดการนัดระหว่างให้คำปรึกษา และผู้ขอรับคำปรึกษา โดยมุ่งเน้นการใช้เทคโนโลยีเข้ามาแก้ปัญหาความไม่สมดุลของข้อมูล ลดขั้นตอนการดำเนินงานที่ซ้ำซ้อน และสร้างระบบนิเวศการที่มีมาตรฐาน ปลอดภัย และเข้าถึงได้ง่ายสำหรับทุกคน 

การนิยามปัญหาและความต้องการ (Problem Definition & VoC) 

การวิเคราะห์ผู้มีส่วนได้ส่วนเสีย (Stakeholder Analysis) 

จากการวิเคราะห์บริบทของปัญหา สามารถจำแนกกลุ่มผู้ใช้งานหลัก และประเด็นปัญหาสำคัญ ได้ดังนี้ : 

กลุ่มผู้ขอรับคำปรึกษา (Advisees) 

คือกลุ่มบุคคลที่ต้องการคำแนะนำเพื่อแก้ปัญหา หรือพัฒนาตนเอง แต่ยังขาดแนวทางที่ชัดเจน 

ปัญหา: ผู้ใช้งานกลุ่มนี้มักเจอปัญหากับภาวะ "ไม่รู้ว่าตนเองไม่รู้อะไร" ทำให้ไม่สามารถสืบค้นข้อมูลได้ตรงจุด อีกทั้งยังขาดความมั่นใจ ในการว่าจ้าง ผู้ให้คำปรึกษาอิสระ เนื่องจากไม่มีระบบคัดกรองหรือรับรองความน่าเชื่อถือที่เพียงพอ 

ความต้องการ: ต้องการระบบที่จะช่วยค้นหาและจับคู่ผู้เชี่ยวชาญที่ตรงกับปัญหาของตน พร้อมระบบที่ช่วยการันตีความปลอดภัยก่อนการชำระเงิน  

 

กลุ่มผู้ให้คำปรึกษา (Advisors) 

คือกลุ่มผู้เชี่ยวชาญที่มีทักษะเฉพาะด้านและต้องการนําไปให้เกิดมูลค่า 

ปัญหา: ปัญหาหลักคืองานที่ไม่ก่อให้เกิดรายได้  เช่น การตอบคำถามซ้ำๆ เพื่อคัดกรองลูกค้า การจัดการนัดหมายที่ทับซ้อน และการติดตามค่าบริการ ซึ่งทำให้กระบวนการทำงาน ขาดความคล่องตัว 

ความต้องการ: ผู้ใช้ต้องการเครื่องมือช่วยบริหารจัดการแบบครบวงจรตั้งแต่การคัดกรองความต้องการลูกค้าการจัดการตารางเวลาอัตโนมัติไปจนถึงระบบรับชำระเงินที่ปลอดภัยเสียงของลูกค้า (Voice of the Customer - VoC) 

สรุปผลการสัมภาษณ์ 

ด้านผู้ให้คำปรึกษา: ปัญหาลูกค้าไม่ทราบความต้องการที่แท้จริงของตนเองรวมถึงปัญหา ความเข้าใจไม่ตรงกันภายในทีม และการขาดความกระตือรือร้นของบุคลากร  

ด้านผู้รับคำปรึกษา: พบปัญหาด้านการหาข้อมูลเฉพาะทาง การค้นหาข้อมูลด้วยตนเองไม่สามารถแก้ได้ นอกจากนี้ยังมีปัญหาเรื่องวัฒนธรรมองค์กรที่แตกต่าง การสื่อสาร ระหว่างแผนกที่ผิดพลาด และความยากในการหาข้อมูลเฉพาะทาง เช่น การจัดซื้อต่างประเทศ 

ความต้องการด้านฟีเจอร์และเครื่องมือบน Platform 

ระบบคัดกรองและจับคู่: ต้องการระบบทำ Screening หรือแบบทดสอบเพื่อระบุความต้องการก่อนเริ่มปรึกษา เพื่อให้มั่นใจว่าจะได้ที่ปรึกษาที่ตรงกับปัญหา  

ความปลอดภัยและความน่าเชื่อถือ: ต้องการระบบยืนยันตัวตน เพื่อป้องกันปัญหา CV/Resume ปลอม และระบบรักษาความลับข้อมูล ที่มีความปลอดภัยสูง  

การจัดการข้อมูล: ต้องการระบบจัดเก็บไฟล์ที่มีประสิทธิภาพ มีระยะหมดอายุที่นาน และสามารถแชร์ให้ทีมงานที่เกี่ยวข้องได้ง่าย 

ความสนใจต่อรูปแบบการให้บริการและราคา 

รูปแบบการชำระเงิน: ผู้ให้สัมภาษณ์ส่วนใหญ่มีราคาที่ยอมรับได้ตั้งแต่ 150 บาทสำหรับปัญหาทั่วไป และ 2,500 บาท สำหรับปัญหาสำหรับองค์กร ตามความยากของปัญหา  

การทดลองใช้งาน: ผู้ให้สัมภาษณ์ทุกคนมีความสนใจและต้องการระบบ ทดลองปรึกษา หรือทดลองใช้งานแอปฟรี เพื่อประเมินความเข้ากันได้ก่อนตัดสินใจจ่ายเงิน
 

ความต้องการที่แท้จริง 

ความต้องการด้านประสบการณ์ 

สิ่งที่ผู้ใช้บอก: ต้องการทดลอง Consult ก่อน และต้องการระบบคัดกรอง  

ความต้องการที่แท้จริง: ผู้ใช้ต้องการลดความเสี่ยงจากการเลือกที่ปรึกษาผิดคน และต้องการสร้างความคุ้นเคย หรือละลายพฤติกรรมกับที่ปรึกษาก่อนที่จะเริ่มเสียค่าใช้จ่ายจริง  

ความต้องการด้านเนื้อหา 

สิ่งที่ผู้ใช้บอก: ข้อมูลในอินเทอร์เน็ตหรือ Large Language Model Chatbot ไม่สามารถแก้ปัญหาได้ เช่น เรื่องวินัยหรือการสื่อสารเฉพาะทาง หรือการขอใบอนุญาติสำหรับงาน  

ความต้องการที่แท้จริง: ต้องการคำแนะนำที่มาจากประสบการณ์จริง และบริบทเฉพาะของปัญหา ซึ่งไม่สามารถหาคำตอบด้วยตัวเองได้ รวมถึงต้องการที่ปรึกษาที่สามารถช่วย ในเรื่องที่ตนเองยังประสบปัญหาได้ 

ความต้องการด้านเทคนิคและการรักษาความลับ 

สิ่งที่ผู้ใช้บอก: กังวลเรื่องความลับรั่วไหล และต้องการปกปิดตัวตน  

ความต้องการที่แท้จริง: ความปลอดภัยของข้อมูลเป็นมูลค่าหลักของ Platform ผู้ใช้ต้องการความมั่นใจว่าการปรึกษาเรื่องส่วนตัวหรือความลับองค์กรจะถูกเก็บรักษาไว้เป็นอย่างดีภายใต้ระบบที่เสถียร  

ความต้องการด้านผลลัพธ์ 

สิ่งที่ผู้ใช้บอก: ยินดีจ่ายเงินหากได้รับผลลัพธ์ที่ดี และต้องการระบบจัดการไฟล์ที่มีประสิทธิภาพ  

ความต้องการที่แท้จริง: ผู้ใช้มองว่า Platform ไม่ได้เป็นเพียงที่พบปะแต่ต้องเป็น เครื่องมือในการทำงาน ที่ช่วยจัดการเอกสาร และข้อมูลจากการปรึกษาให้เป็นระเบียบ และนำไปใช้ต่อได้จริง
 

ข้อกำหนดที่วัดผลได้ (Quantifiable Requirements - QRs) 

เพื่อให้สอดคล้องกับความต้องการของผู้ใช้งานและสถาปัตยกรรมของ Advisory Platform สามารถกำหนด Matrix ที่ตรวจสอบได้ในส่วนสำคัญของโครงงาน ดังนี้ 

ด้านการตอบสนองของระบบ 

การแสดงผลหน้าเว็บ: แอปพลิเคชันต้องสามารถโหลดและแสดงผลหน้าหลัก และหน้าค้นหาที่ปรึกษาได้ภายใน 3 วินาที (ภายใต้การเชื่อมต่ออินเทอร์เน็ตมาตรฐาน) 

ความหน่วงของระบบแชท: ระบบ Chat Feature ต้องใช้เวลาในการซิงค์และแสดงผลข้อความระหว่างผู้ใช้งานไม่เกิน 500 มิลลิวินาที 

ด้านการสื่อสารผ่านวิดีโอ 

ความเสถียรของ Video Call: การเชื่อมต่อการสนทนา ต้องรองรับความละเอียดวิดีโอระดับมาตรฐาน โดยมีความหน่วงต่ำกว่า 150ms และมีอัตราข้อมูลสูญหายไม่เกิน 5% เพื่อให้การให้คำปรึกษาเป็นไปอย่างราบรื่น (ภายใต้การเชื่อมต่ออินเทอร์เน็ตมาตรฐาน) 

ด้านการจัดการข้อมูลและไฟล์ 

การอัปโหลดและจัดเก็บไฟล์: ระบบจัดการไฟล์ผ่านฐานข้อมูล ต้องรองรับการอัปโหลดไฟล์ขนาดสูงสุด 50 MB ต่อครั้ง และสามารถจัดเก็บไฟล์ได้อย่างยาวนาน

Software Requirements & Tech Stack 

Frontend: พัฒนาด้วยเทคโนโลยีเว็บสมัยใหม่ เช่น React.js ควบคู่กับ Next.js โดยใช้ภาษา TypeScript ในการพัฒนา เพื่อให้ระบบรองรับการทำ Progressive Web App และออกแบบส่วนติดต่อผู้ใช้ด้วย Tailwind CSS เพื่อให้รองรับการแสดงผลแบบ Responsive ทุกหน้าจอ 

Backend & API: พัฒนาด้วย Node.js ผ่าน Next.js เพื่อสร้าง RESTful API สำหรับจัดการลอจิกของระบบ 

Database & Storage: ใช้บริการของ Supabase ทำหน้าที่เป็นฐานข้อมูลหลัก โดยใช้งาน DBMS PostgreSQL เพื่อจัดเก็บข้อมูลผู้ใช้ ประวัติการทำธุรกรรม และการจองเวลา รวมถึงใช้ระบบ Object Storage ของ Supabase ในการจัดการไฟล์เอกสาร พร้อมระบบจำกัดสิทธิ์การเข้าถึงไฟล์ 

Third-party Integrations: มีการเชื่อมต่อ Video Call Module เข้ากับ 8x8 Jitsi Meet ที่ Host ด้วยตนเอง เพื่อสร้างห้องประชุมและจัดการลิงก์นัดหมาย และเชื่อมต่อ Payment Module กับ Payment Gateway ผ่าน OMISE สำหรับประมวลผลการรับชำระเงิน และโอนรายได้ให้ผู้ให้คำปรึกษา 

DevOps: ใช้ Docker ในการบรรจุและจำลองสภาพแวดล้อมการทำงาน เพื่อให้การ Deploy มีความเสถียร และมีการจัดการ CI/CD Pipelines เพื่อทำ Automated Testing ทั้ง Unit test และ Integration test  

ข้อกำหนดด้านการสื่อสาร 

HTTPS/REST: ใช้สำหรับสื่อสารระหว่าง Frontend และ Backend API โดยข้อมูลทั้งหมดต้องถูกเข้ารหัสผ่าน SSL/TLS  

WebSocket: ใช้สำหรับโมดูล Chat และ Real-time Notification เพื่อให้สามารถซิงค์ข้อมูลระหว่างผู้ใช้งานสองฝั่งได้ทันทีโดยมีความหน่วงต่ำ 

WebRTC: โปรโตคอลหลักที่ถูกเรียกใช้ผ่าน Jitsi Meet สำหรับการสตรีมภาพและเสียงแบบ Peer-to-Peer ในระบบ Video Meeting

การวิเคราะห์เชิงวิศวกรรม (Engineering Analysis) 

การประเมินความเป็นไปได้เบื้องต้น ของระบบ Advisory Platform ภายใต้สมมติฐานการทดสอบระบบด้วย Load Testing ที่มีผู้ใช้งานพร้อมกัน Concurrent Users จำนวน 1000 คน มีรายละเอียดการคำนวณดังนี้ 

การวิเคราะห์ความต้องการแบนด์วิดท์ของเครือข่าย 

ฟีเจอร์ที่ใช้ทรัพยากรเครือข่ายสูงสุดคือโมดูล Video Call และ Chat 

สมมติฐาน: ในจำนวนผู้ใช้ 1000 คนพร้อมกัน มีผู้ใช้งานที่กำลังวิดีโอคอลแบบ 1-ต่อ-1 จำนวน 20 คู่ (40 คน) และใช้งานแชท/ค้นหาข้อมูล จำนวน 400 คน 

การคำนวณ Video Call: การสตรีมวิดีโอความละเอียด 1280x720 pixels ผ่าน WebRTC โดยเฉลี่ยใช้แบนด์วิดท์ประมาณ 1.5 Mbps ต่อคน  

การคำนวณข้อความและ API: การรับส่งข้อมูลผ่าน REST API และ WebSocket สำหรับ 60 คน ใช้แบนด์วิดท์เฉลี่ยไม่เกิน 5 Mbps 

สรุปความเป็นไปได้: ระบบต้องการแบนด์วิดท์รวมขั้นต่ำประมาณไม่เกิน 1 Gbps ซึ่ง Server ในปัจจุบัน  มีพอร์ตเครือข่ายระดับ 1 Gbps  เป็นมาตรฐาน จึงยืนยันได้ว่าระบบจะไม่เกิดปัญหาคอขวด และสามารถรักษาความหน่วงให้ต่ำกว่าเกณฑ์ 250 มิลลิวินาทีได้ 

การวิเคราะห์ปริมาณการจัดเก็บข้อมูล (Storage Estimation) 

สมมติฐาน: แพลตฟอร์มมีผู้ใช้งานที่ลงทะเบียน 1,000 คน โดยเฉลี่ยแต่ละคนมีการอัปโหลดเอกสารหรือรูปภาพคนละ 3 ไฟล์ ขนาดเฉลี่ยไฟล์ละ 10 

การคำนวณ File Storage: ปริมาณข้อมูลไฟล์รวมเท่ากับ 30 GB 

สรุปความเป็นไปได้: บริการฐานข้อมูลบนคลาวด์ เช่น Supabase ในแพ็กเกจระดับเริ่มต้น-กลาง รองรับพื้นที่จัดเก็บข้อมูลได้ 100 GB ซึ่งครอบคลุมปริมาณการใช้งาน 31 GB ที่คำนวณได้อย่างเพียงพอ

ข้อจำกัดที่สมจริง (Realistic Constraints) 

ด้านเศรษฐศาสตร์ 

ระบบทำงานบนคลาวด์ทำให้มีค่าใช้จ่ายแฝง ที่แปรผันตามปริมาณการใช้งาน โครงงานจึงจัดการด้วยการจำกัดโควตาขนาดไฟล์อัปโหลดสูงสุดไม่เกิน 50 MB ต่อครั้ง ควบคู่กับการตั้งค่าระบบแจ้งเตือนงบประมาณบน Cloud Provider เพื่อป้องกันค่าใช้จ่ายบานปลาย นอกจากนี้ยังมีการคำนวณต้นทุนค่าธรรมเนียมของ Payment Gateway รวมเข้าไปในโครงสร้าง Platform Fee เพื่อให้โมเดลธุรกิจมีความเป็นไปได้และกระแสเงินสดไม่ติดลบ 

ด้านความปลอดภัยและความเป็นส่วนตัว 

แพลตฟอร์มต้องจัดเก็บข้อมูลที่มีความอ่อนไหวภายใต้ข้อบังคับ PDPA จึงจัดการโดยเปิดใช้งานการจัดการสิทธิ์ระดับฐานข้อมูล เพื่อล็อกสิทธิ์การเข้าถึงข้อมูลเฉพาะเจ้าของบัญชี มีการใช้ JWT ในการยืนยันตัวตนและเข้ารหัสรหัสผ่าน ก่อนลงฐานข้อมูล รวมถึงการสร้างแบบฟอร์มขอความยินยอมก่อนสมัครสมาชิก และพัฒนาระบบให้ผู้ใช้สามารถลบบัญชีและข้อมูลตนเองได้เพื่อรองรับสิทธิการถูกลืม
 

ด้านจริยธรรม 

เพื่อป้องกันการละเมิดลิขสิทธิ์และการใช้ข้อมูลผิดวัตถุประสงค์ โครงงานจะตรวจสอบไลบรารีและเครื่องมือทั้งหมดให้เป็นสัญญาอนุญาตแบบ Open-source ที่อนุญาตให้ใช้เชิงพาณิชย์ได้ ในขั้นตอนการทดสอบ จะใช้เครื่องมือสร้างข้อมูลจำลอง แทนการดึงข้อมูลจริงของผู้ใช้บนอินเทอร์เน็ตเพื่อไม่ให้ละเมิดสิทธิส่วนบุคคล และมีการพัฒนาระบบคัดกรองเนื้อหาผ่านฟีเจอร์ Report เพื่อให้ผู้ใช้สามารถรายงานพฤติกรรมหรือการให้คำปรึกษาที่ผิดจริยธรรมวิชาชีพ ไปสู่ผู้ดูแลระบบได้ 

ด้านความยั่งยืน

เกณฑ์การประเมินความสำเร็จ (Success Criteria) 

เกณฑ์ด้านความถูกต้องของอัลกอริทึมจัดตารางเวลา 

สำหรับอัลกอริทึมระบบจัดตารางเวลาต้องทำงานได้อย่างถูกต้องแม่นยำ โดยมีเงื่อนไขข้อจำกัด ว่าเวลาเริ่มต้นและเวลาสิ้นสุดของการนัดหมายในแต่ละช่วงเวลาของผู้ให้คำปรึกษาจะต้องไม่ทับซ้อนกันเลยในทุกกรณี ระบบต้องสามารถตรวจสอบและป้องกันการทับซ้อนนี้ได้สำเร็จร้อยเปอร์เซ็นต์ในทุกๆ การทำธุรกรรมจองเวลา เพื่อรักษาความถูกต้องของข้อมูลในระบบ 

Modular Robustness 

โครงสร้างซอฟต์แวร์ต้องมีคุณภาพ และผ่านการตรวจสอบเพื่อยืนยันว่าการแก้ไขระบบส่วนหนึ่งจะไม่ส่งผลกระทบต่อระบบส่วนอื่น โดยระบบจะต้องผ่านกระบวนการทำ Automated Testing ซึ่งประกอบด้วย Unit Testing สำหรับทดสอบการทำงานระดับฟังก์ชัน และ Integration Testing สำหรับทดสอบการทำงานระดับ API โดยจะต้องมีผลลัพธ์ความครอบคลุมของการทดสอบ Code Coverage ไม่ต่ำกว่าร้อยละ 80 ของโค้ดทั้งหมด และต้องไม่พบข้อผิดพลาดระดับวิกฤตที่ทำให้ระบบหยุดการทำงาน 

เกณฑ์ด้านการรองรับ Scalability & Load Testing 

สถาปัตยกรรมของระบบต้องสามารถรองรับปริมาณการใช้งานพร้อมกันได้โดยไม่เกิดการล่มเมื่อทำการทดสอบประสิทธิภาพด้วยเครื่องมือจำลองโหลด ระบบจะต้องสามารถรองรับผู้ใช้งานที่เข้ามาใช้งานพร้อมกันได้อย่างน้อย 1000 คน  

เกณฑ์เชิงการประเมินการใช้งานจริง 

แพลตฟอร์มต้องสามารถตอบโจทย์ผู้ใช้งานและสร้างประสบการณ์ที่ดีได้จริง เมื่อนำระบบไปทดสอบการยอมรับของผู้ใช้ หรือ User Acceptance Testing กับกลุ่มตัวอย่างผู้รับคำปรึกษาและผู้ให้คำปรึกษา ผลประเมินความพึงพอใจรวมตามหลักการวัดความสามารถในการใช้งานระบบจะต้องไม่ต่ำกว่าร้อยละ 80 นอกจากนี้ผู้ใช้งานกลุ่มทดสอบต้องมีอัตราความสำเร็จในการทำกระบวนการหลักของฟีเจอร์ เช่น การค้นหาที่ปรึกษาและการจองเวลา ได้สำเร็จด้วยตนเองไม่ต่ำกว่าร้อยละ 90 โดยไม่ต้องพึ่งพาคู่มือการใช้งาน

Design Methodology & Rationale 

สถาปัตยกรรมซอฟต์แวร์ 

การเลือกใช้ Tech Stack ไม่ได้เลือกตามความนิยม แต่เลือกตามข้อกำหนดทางวิศวกรรม 

Next.js (Frontend): เลือกเพราะความสามารถในการทำ Server-Side Rendering (SSR) และ Progressive Web App (PWA) ซึ่งช่วยลด Latency ในการโหลดหน้าแรกให้ต่ำกว่า 3 วินาทีตามที่กำหนดใน QR 

NestJS (Backend): เลือกใช้ Node.js framework นี้เพราะโครงสร้างที่เป็น Modular Architecture และรองรับ TypeScript อย่างเต็มรูปแบบ ทำให้การทำ Automated Unit Testing มี Code Coverage เกิน 80% ได้ง่ายขึ้น 

Supabase (Database/Storage): เลือกใช้แทน SQL ทั่วไปเพราะมีระบบ Real-time Engine ผ่าน WebSockets ซึ่งจำเป็นต่อระบบ Chat และ Notification โดยไม่ต้องตั้งค่าเซิร์ฟเวอร์เองเพิ่มเติม 

ระบบสื่อสารและเครือข่าย 

WebRTC via Jitsi API: เราเลือกใช้โปรโตคอล WebRTC เพราะเป็นการสื่อสารแบบ Peer-to-Peer (P2P) ซึ่งช่วยลดภาระของเซิร์ฟเวอร์กลางและลดความหน่วง (Latency) ได้ดีที่สุดสำหรับการสื่อสารแบบ 1-ต่อ-1 

Data Modeling Rationale 

สถาปัตยกรรมฐานข้อมูลถูกออกแบบในรูปแบบ Relational Database Model โดยใช้ PostgreSQL บน Supabase เพื่อรองรับความถูกต้องของธุรกรรม (ACID Compliance) และความปลอดภัยของข้อมูล 

Separation of User Roles: การใช้ตาราง USERS เป็นศูนย์กลางและเชื่อมต่อแบบ 1-to-1 กับ ADVISOR_PROFILES และ ADMIN_PROFILES ช่วยเพิ่มประสิทธิภาพในการจัดการสิทธิ์ (Access Control) และสอดคล้องกับหลักการ Database Normalization เพื่อลดความซ้ำซ้อนของข้อมูลฃ 

Temporal Data Integrity: ตาราง SERVICE_TIMESLOTS ถูกออกแบบมาเพื่อรองรับเงื่อนไข No-Overlap Constraint ในระดับฐานข้อมูล. ข้อมูลวันและเวลาจะถูกเก็บในรูปแบบ datetimetz (Timezone-aware) เพื่อป้องกันข้อผิดพลาดจากความต่างของเขตเวลา (Time zone) ตามที่ผู้ใช้กังวล 

Global Uniqueness: การใช้ UUID เป็น Primary Key ในทุกตาราง แทนการใช้ Auto-increment Integer. เหตุผลทางวิศวกรรมคือเพื่อรองรับการขยายตัวของระบบในระดับ Distributed System และเพิ่มความปลอดภัยในการเข้าถึงข้อมูลผ่าน URL ที่คาดเดายาก
